# M1-9 存储位置：缩略图、转码视频、数据库备份和各用户原图放到群晖

- 日期：2026-10-30
- 分支：`mac/feat/storage-locations`
- 结论：**通过**。在"管理 → 存储位置"里，可以把缩略图、转码视频、数据库备份和每个用户的原图放到已挂载的群晖共享上，现有文件在后台迁移过去。群晖不在线时，用到它的任务自动暂停，不会把文件误写到 Mac 上；群晖恢复后自动继续。端到端 42/42 通过，服务端单测 2544 项全部通过

## 怎么用

1. 先在"管理 → 网络共享"里挂载群晖（见 [m1-network-shares.md](m1-network-shares.md)），必须是可读写
2. 管理 → **存储位置**，分两部分：
   - **Immich 生成的文件**：缩略图和预览图、转码视频、数据库备份。点"编辑"，选择共享，填共享上的文件夹（默认建议 `immich/thumbs` 这样的单独目录）
   - **每个用户的原图**：手机备份和网页上传的照片、视频。例如在 `homes` 共享上填 `<用户>/Photos/Immich`。**需要先开启存储模板**，原图是靠"存储模板迁移"搬过去的
3. 保存后，现有文件在后台迁移，页面上显示进度

推荐的群晖目录：

| 内容 | 群晖上的位置 |
|---|---|
| 缩略图、转码视频、数据库备份 | 新建一个共享文件夹（如 `immich`），下面分 `thumbs`、`encoded-video`、`backups`。不放进 homes，群晖 Photos 不会去索引；有 SSD 卷或 SSD 缓存的话放在上面 |
| 用户原图 | `homes/<用户>/Photos/Immich`，和老照片放在一起 |
| 老照片 | 外部库导入 `homes/<用户>/Photos`。**不需要手动加排除规则**，外部库会自动跳过 `Immich` 这个目录 |

始终留在 Mac 上的：**数据库**（PostgreSQL 放在 NFS 上会损坏）、**识别模型**（H-14 约 21 GB，空闲 5 分钟会卸载，从群晖重新读太慢）、**上传暂存区**（很小；群晖不在线时手机照样能备份）、头像。

## 实现

| 部分 | 内容 |
|---|---|
| 接口 | `admin/storage-locations`：查看、设置文件夹的位置、设置用户原图的位置，仅管理员可用。和网络共享一样，只在 macOS 原生安装下可用 |
| 存储 | 位置存在数据库的 `system_metadata`（`storage-locations`），记的是"哪个共享 + 共享上的路径"，不是绝对路径：共享改名不影响 |
| 路径 | `StorageCore.getBaseFolder()` 和 `getLibraryFolder()` 改为先查位置设置，其他代码不用改。每个工作进程启动时读取设置，修改后通过服务端事件通知所有进程重新读取 |
| 设置时的检查 | 共享必须已挂载、能响应、可读写；路径不能是共享根目录、不能含 `..`；文件夹必须是空的或者新建的（群晖和访达留下的 `@eaDir`、`.DS_Store` 等不算）；不能和别的位置重叠；不能有外部库从它**里面**导入。通过后建好目录并写入标记文件 `.immich` |
| 迁移 | 后台任务 `StorageLocationMigration`：同一个盘上直接重命名；跨盘先复制、比较大小、保留修改时间，再删除原文件，最后更新数据库里的路径（只在路径没被别的任务改过时才更新）。连续失败 20 次就停下（多半是群晖断开了），等下一次检查再继续。数据库备份不在数据库里登记，按目录逐个文件搬 |
| 原图迁移 | 改用户位置后自动排队"存储模板迁移"，复用上游已有的搬移和校验逻辑 |
| 每分钟检查 | 网络共享的每分钟检查结束后，报告哪些共享可用；存储位置据此检查每个位置（共享可用 + 标记文件在）。不可用就**暂停**用到它的任务队列，恢复后**自动继续**；你自己手动暂停的队列不会被它恢复。还有没迁完的文件时，可用后自动接着迁 |
| 不会误写到 Mac | 挂载点在没挂载时设为只读（`555`），挂上之后用群晖自己的权限。群晖断开期间，任何写入都会直接失败，不会悄悄写进 Mac 的空目录（否则会占满磁盘，挂上后还会被盖住看不到） |
| 启动 | 服务端启动时只检查 Mac 上照片库目录本身，不检查群晖上的位置，所以群晖不在线时服务端照样能启动，任务保持暂停 |
| 外部库 | 扫描、监视文件变化、离线检查都会跳过存储位置里的文件，所以从 `<用户>/Photos` 导入的外部库不会把 `Photos/Immich` 里的照片再导入一遍 |
| 保护 | 有位置在用的共享不能删除，也不能改成只读。删除用户时，群晖上的原图目录只删空文件夹，不整个删（里面可能有用户自己放的文件）；用户的照片在这之前已经随用户一起删掉 |
| 网页 | 管理菜单新增"存储位置"：两张表（生成的文件、每个用户的原图），状态徽标（可用 / 正在迁移 / 不可用）、原因、迁移进度；有任务因此暂停时页面顶部提示；存储模板没开时提示先开。每 15 秒自动刷新。en / 简体中文 / 繁体中文 |

## 用户之间的隔离（分支 `mac/fix/user-isolation`）

隔离在 Immich 内部做，不靠群晖的权限：Mac 用同一个身份挂载群晖共享，群晖上 `homes` 的权限对 Immich 不起作用。

### 审查结论：非管理员碰不到文件路径

| 入口 | 谁能用 |
|---|---|
| 外部库：创建、修改导入路径、校验、扫描 | 只有管理员（`admin: true`）；库建好后不能改所有者 |
| 网络共享：添加、挂载、测试（列出顶层 20 项） | 只有管理员；没有任何通用的目录浏览接口 |
| 存储位置、存储标签 | 只有管理员；用户自己的资料接口里没有这两个字段 |
| 查看照片、下载、文件夹视图、上传查重 | 一律按照片的所有者判断，另外只有相册共享、伙伴共享、分享链接这三种用户自己授权的方式 |
| 上传 | 没有路径参数，文件名由服务端生成 |

外部库导入的照片一律归库的所有者，所以"谁能看到什么"取决于管理员把哪个目录配给谁的库。

### 补上的三处

| 问题 | 修复 |
|---|---|
| 存储模板的边界检查用的是 `startsWith(rootPath)`，不带 `/`。用户目录在群晖上是并列的，若模板用了 `{{make}}`、`{{model}}`、`{{lensModel}}`（取自用户上传文件的 EXIF，未清理），一个伪造了相机型号 `../<名字相同开头的目录>` 的文件可能被移到旁边的目录。当前模板 `{{y}}/{{MM}}/{{filename}}` 不受影响 | 改用带 `/` 的 `isWithin`；单测在修复前失败、修复后通过 |
| 外部库的导入路径不检查归属：管理员误把 `homes` 整个配给某人的库，其他人的照片会被导入成这个人的 | 导入路径如果包含**其他用户**的存储位置，校验和扫描时都拒绝；反过来，给用户设存储位置时，如果它在**其他用户**库的导入路径之下，也拒绝。用户自己的库包含自己的 `Photos/Immich` 照常允许（扫描时跳过） |
| 扫描跳过 Immich 目录只按路径字符串比较：同一个群晖目录如果从另一条路径挂进来（比如 Finder 里的 `/Volumes/homes`），就认不出来 | 扫描和监听时，跳过任何带 `.immich` 标记文件的目录，不论从哪条路径到达；每个目录只查一次 |

服务端单测 2573 项全部通过。

### 配置建议

- 每个用户一个外部库，所有者选这个用户，导入路径只填他自己的 `homes/<用户>/Photos` 下的目录。
- 每个用户的存储位置设在他自己的 `homes/<用户>/Photos/Immich`。
- 外部库的路径用"网络共享"里挂载的路径，不要用 Finder 挂载的 `/Volumes/...`。
- 不要开启"伙伴共享"或建共享相册，除非你确实想共享。
- 管理员账号能看到所有设置，但看不到其他用户的照片，除非他们分享给你。
