# M1-10 视频旋转、镜像，以及查看时一键旋转

- 日期：2026-10-30
- 分支：`mac/feat/video-rotate`
- 结论：**通过**。视频现在可以像照片一样旋转和镜像（裁剪除外）；查看照片或视频时按 `R` 顺时针转 90°、`Shift+R` 逆时针转 90°，"更多"菜单里也有。视频旋转不重新编码，只改写视频的显示方向，几秒完成，画质无损，原文件不动。端到端 49/49，浏览器 11/11，服务端单测全部通过

## 为什么原来不行

Immich 的编辑（裁剪、旋转、镜像）是非破坏性的：原文件不动，按编辑重新生成缩略图和预览。服务端只对图片做了这件事（`asset.service.ts` 遇到视频直接拒绝："Only images can be edited"），网页上视频也不显示"编辑"按钮。视频难在播放：浏览器、手机 App、实时转码播放的都是视频文件本身。

## 做法

MP4、MOV 里有一个"显示矩阵"，告诉播放器画面要转多少度、要不要翻转。所有播放器（浏览器、iOS、Android、ffmpeg）都会按它显示。所以视频的旋转和镜像，只需要把视频流**原样复制**一份，换上新的显示矩阵（ffmpeg `-display_rotation`、`-display_hflip`，`-c copy`）：

- 不重新编码：画质无损，一段 3 秒的视频 3 秒内完成（大部分时间是排队和生成缩略图），大视频也只是复制一次文件的时间
- 原文件不动，撤销编辑就删掉这份副本
- 裁剪做不到（要重新编码），所以视频只能旋转和镜像

| 部分 | 内容 |
|---|---|
| 换算 | `server/src/utils/video-edit.ts`：编辑（顺时针旋转、水平或垂直镜像，按顺序）加上视频本身的旋转，换算成显示矩阵（逆时针旋转角度 + 是否水平翻转）。8 种组合的对应关系是**逐帧实测**出来的：同一帧分别用图片编辑（sharp）和改写显示矩阵后的视频解出来比较。4 种源旋转（0、90、-90、180）× 28 种编辑组合共 112 种全部一致 |
| 播放的视频 | 编辑后生成 `encoded-video/…/<id>_edited.mp4`：有转码版本就复制转码版本，否则复制原文件；先读出它自己的旋转再叠加。`/video/playback` 优先给这份。视频重新转码后自动重新生成 |
| 缩略图、尺寸 | 编辑后的预览图和缩略图从原文件生成，读取时直接按新的显示矩阵；资产宽高按旋转后的尺寸更新（时间线、播放器的比例都对）。原来的缩略图保留 |
| 下载 | "下载"给编辑后的 mp4，"下载原件"给原文件 |
| 实时转码（HLS） | 读原文件时加上新的显示矩阵，各档分辨率按旋转后的方向计算。仍然用原文件，因为分段是按原文件的关键帧算的 |
| 撤销 | 删除编辑后：副本和编辑版缩略图删除，尺寸和缩略图哈希恢复 |
| 失败时 | 个别格式不能原样复制进 mp4 时，记一条错误日志，视频按原样播放，不影响其它 |
| 上游 bug | 读编辑列表的子查询（`withEdits`）没按顺序排序。镜像和旋转的先后不同，结果就不同，图片也受影响。已加上按 `sequence` 排序 |

### 网页

| 部分 | 内容 |
|---|---|
| 一键旋转 | 查看照片或视频时：`R` 顺时针 90°、`Shift+R` 逆时针 90°，"更多"菜单里有"顺时针旋转 90 度""逆时针旋转 90°"。保存为编辑，和编辑器里的旋转是同一个东西，可以在编辑器里撤销或继续改。连按几次会累加，不会丢；转回原样时编辑自动删除。转完后当前画面直接刷新，不用重新打开 |
| 编辑器 | 视频也显示"编辑"按钮（按 `E`）：在视频的预览图上旋转、翻转，没有裁剪栏和裁剪框 |
| 等待时间 | 等服务端处理完的超时，照片 30 秒，视频 5 分钟（大视频在群晖上复制要时间）。原来是 10 秒 |

一键旋转对新视频的计算（`web/src/lib/utils/asset-rotate.ts`）：已有旋转时在原角度上加；旋转后面跟着镜像时要反方向加（镜像会把后面的旋转方向反过来）。

## 端到端（`macos/scripts/m1_video_rotation.py`）

在隔离的测试实例上运行（`local.immich-p7`，端口 2290，默认 VideoToolbox 硬件转码）。素材：横屏 mp4（直接播放）、竖拍 mov（存储为横屏 + 显示矩阵 -90°，和 iPhone 竖拍一样）、MPEG-4 的 avi（需要转码）。

**判定方法**：先取视频当前显示的一帧，作为一张图片上传到 Immich。然后对视频和这张图片做同样的编辑，比较视频播放出来的画面和服务端图片编辑出来的结果。这样验证的是"视频和照片的编辑结果完全一致"，不依赖我对方向的理解。

| 场景 | 结果 |
|---|---|
| 横屏 mp4：顺时针 90° | 通过：画面差异 2.1/255；流原样复制（字节数相同）；尺寸 1280×720 → 720×1280；预览图竖了，原预览保留；下载为编辑版；原文件不变 |
| 竖拍 mov：先水平镜像、再转 90° | 通过：差异 3.3 |
| 需转码的 avi：转 270° | 通过：差异 2.2；复制的是转码后的 mp4 |
| 横屏 mp4：垂直镜像 | 通过：差异 2.1 |
| 竖拍 mov：先转 180°、再水平镜像 | 通过：差异 2.4 |
| 编辑后重新转码 | 通过：副本按新的转码版本重新生成，仍然是转过的 |
| 撤销编辑 | 通过：副本和编辑版缩略图删除，尺寸恢复，播放恢复原样 |
| 裁剪视频 | 通过：拒绝，提示"Videos can only be rotated and mirrored" |
| 实时转码（HLS）：竖拍 mov 镜像 + 转 90° | 通过：各档分辨率变成横向（852×480、1280×720）；取第一段解出来与图片编辑结果差异 3.4 |

第一次运行 47/49：两项失败都是测试素材的问题。mkv 里的 H.264 本来就不需要转码（容器按 webm 被接受）；判断"副本是否重新生成"用了数据库时间戳，同一路径 upsert 时它不变。换成 MPEG-4 的 avi、改看文件修改时间后 49/49。

## 已知限制

- **官方手机 App**：视频如果还在这台手机的相册里，App 会直接播放手机上的文件，不会转；不在手机上的（别的设备传的、群晖外部库里的）会转。缩略图都会转。这是 App 自己的逻辑，服务端改不了
- 网页上"播放原始视频"播放的是原文件，不会转
- 视频不能裁剪
