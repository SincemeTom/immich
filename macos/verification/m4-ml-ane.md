# M4-1 机器学习模型用 fp16，在神经网络引擎（ANE）上运行

- 分支：`mac/feat/ml-v2-ane`、`mac/fix/release-ml-deps`（都已合入 `mac/develop`）
- 安装包：`Immich-3.3.5-dev-a559bb0f5.pkg`（开发版，已公证）
- 结论：**通过**。三个模型都换成上游的 v2 导出，服务在本机把它转成 fp16，CoreML 把它放到 ANE 上运行。智能搜索、人脸、OCR 的结果与原来一致，速度快约一倍，内存只有原来的四分之一左右；已有的搜索索引和人脸聚类**不需要重建**

## 原因：ANE 只运行 fp16

正式环境第一次导入几万张照片时，GPU 98%、ANE 0%。原来的模型（`main` 导出）全是 fp32，ANE 不能运行 fp32，CoreML 只能把它们都放到 GPU 上。

Immich 上游已经为每个模型发布了 v2 导出（Hugging Face 上的 `v2` 分支），设置 `MACHINE_LEARNING_MODEL_REVISION=v2` 就会使用：

- 下载的权重仍是 fp32（safetensors），服务在本机准备模型时转成 fp16（`immich_model.onnx.f16`），超出 fp16 范围的值截断而不是变成 0 或无穷大
- 再按运行设备改写计算图：例如专门为 ANE 拆分过深的矩阵乘法（`split_deep_reduction`）
- CPU 上仍用 fp32

这是上游支持、带测试的路径，不是我们自己转换模型。

## 改动

| 位置 | 改动 |
|---|---|
| `run-service` | 机器学习服务和预热都使用 v2（`MODEL_REVISION=v2`）；在 `native.env` 里设 `IMMICH_NATIVE_MODEL_REVISION=main` 可以换回原来的 |
| `immich_ml/sessions/prepare.py` | 准备 CoreML 计算图时，比较"CoreML 自选运行单元"和"只用 ANE"的耗时，只用 ANE 快 20% 以上时改为只用 ANE，记在计算图的清单里（见下） |
| `immichctl warm` | 换成 v2 时，先清掉 CoreML 为旧导出编译的系统缓存（`~/Library/Caches/python/com.apple.e5rt.e5bundlecache`），v2 准备好后删掉旧导出及其编译结果 |
| 安装包 | 打包 v2 模型（`stage_models.py` 已按导出版本存放）；`postinstall` 按模型的完成标记放置，v2 放在旧导出旁边，不覆盖 |

### 为什么要自己比较运行单元

CoreML 自选（`MLComputeUnits=ALL`）时，大多数计算图都放对了，但 OCR 的文字检测被拆在 GPU 和 ANE 之间，比只用 ANE 慢将近一半到三分之二：

| 计算图 | CoreML 自选 | 只用 ANE | 选择 |
|---|---|---|---|
| OCR 检测 1024×1024 | 33.3 ms | 17.7 ms | 只用 ANE |
| OCR 检测 1376×1024（常见竖图） | 43.0 ms | 23.0 ms | 只用 ANE |
| OCR 检测 1024×2048（长图） | 103.9 ms | 36.4 ms | 只用 ANE |
| 人脸识别（每次 1 张脸） | 2.3 ms | 1.6 ms | 只用 ANE |
| 智能搜索 图像 | 42.9 ms | 42.5 ms | 不变（CoreML 已经放在 ANE） |
| 智能搜索 文字 | 6.8 ms | 5.8 ms | 不变 |
| 人脸检测 | 2.9 ms | 2.9 ms | 不变 |
| OCR 识别（一次 6 行） | 16.6 ms | 175.2 ms | 不变（CoreML 放在 GPU，只用 ANE 慢 10 倍） |

比较只在第一次准备时做一次（每个计算图几秒），结果写进计算图的清单，之后直接按它加载。

## 测试（这台 Mac：M4 Pro 64 GB；目标机 M4 16 GB 的绝对速度会慢一些，比例相近）

### 速度（服务端调用方式，热启动中位数）

| 任务 | 原来（main，fp32） | v2（fp16） | 加速 |
|---|---|---|---|
| 智能搜索 图像 | 94.1 ms | 51.5 ms | 1.83× |
| 智能搜索 文字 | 20.0 ms | 8.9 ms | 2.25× |
| 人脸（检测 + 识别） | 27.0 ms | 13.5 ms | 2.00× |
| 人脸，标注集每张照片 | 63 ms | 41 ms | 1.54× |
| OCR，真实照片每张 | 111 ms | 86 ms | 1.29× |

### 结果是否一致

| 项目 | 原来 | v2 |
|---|---|---|
| 智能搜索 中文 recall@1 / @3 / @5 | 90.0% / 96.7% / 100% | 90.0% / 96.7% / 100% |
| 智能搜索 英文 recall@1 / @3 / @5 | 90.0% / 100% / 100% | 90.0% / 100% / 100% |
| 图像、文字向量与原来的余弦相似度 | — | 0.9989–0.9996 |
| 人脸 45 张检出 / 同一人配对 / 不同人误判 / AUC | 45 / 54 of 64 / 0 of 926 / 0.999 | 45 / 54 of 64 / 0 of 926 / 0.999 |
| 人脸向量与原来的余弦相似度 | — | 0.9993 |
| OCR 真实照片 / 合成 / 困难 / 繁体 / 日文 | 57/58 / 58/60 / 52/60 / 8/12 / 10/14 | **58/58** / 58/60 / 52/60 / 8/12 / 10/14 |

### 内存（三个模型都加载，处理测试照片）

| 项目 | 原来 | v2 |
|---|---|---|
| 服务进程 | 峰值 5.9 GB | 1.3 GB |
| **整台 Mac 增加的内存占用**（匿名 + 联动 + 压缩内存） | **+6.0 GB** | **+1.6 GB** |
| 模型目录（含编译结果） | 30.3 GB | 13.7 GB |
| CoreML 系统缓存 | 约 10 GB 起 | 1.0 GB |

ANE 的模型权重以文件映射的方式加载，内存紧张时系统可以丢弃再从磁盘读回，不会占着不放。16 GB 的机器上，机器学习从"占掉三分之一以上"变成"约 1.6 GB"。

### 升级（`macos/native/install.sh` 升级一个用原来模型、已有照片的实例）

| 项目 | 结果 |
|---|---|
| 升级前：端到端 | 36/36 |
| 升级：预热 | 7 分 39 秒（v2 全部重新编译 + 比较运行单元；只有第一次）；清掉 CoreML 系统缓存；删除旧导出：智能搜索 24 → 11 GB、人脸 1.6 GB → 707 MB、OCR 4.7 → 2.0 GB |
| 用升级前的索引搜索 8 条中英文查询 | 第一名 8/8 相同；后面几名在不相关的图片之间互换位置 |
| 升级后重新计算全部向量，与升级前存的比较 | 智能搜索 26 个：最低 0.9983，平均 0.9993；人脸：0.9995 |
| 升级后：端到端 | 36/36 |

结论：**升级后不需要重新跑智能搜索和人脸识别**，原来的索引照样能用；新照片用 v2 计算，与旧照片可以一起搜索、一起聚类。

### 安装包（自带依赖的发布目录，屏蔽 Homebrew、不能联网）

第一次测试新装时，**人脸和 OCR 全部失败**（端到端 40/42）：服务日志里每个请求都是 `module 'cv2' has no attribute 'convertFp16'`。

原因在打包脚本：锁文件特意用"覆盖"去掉了 `opencv-python`，只装无界面版 `opencv-python-headless` 4.14。一键安装用 `uv sync` 会遵守这一点；而打包脚本把锁文件导出成依赖清单再 `uv pip install`，安装时又重新解析了一遍依赖，`rapidocr` 依赖 `opencv-python`，于是装上了最新的 5.0。两个包装进同一个 `cv2` 目录，混出来的 `cv2` 缺 `convertFp16`。原来的 fp32 模型用不到这个函数，所以以前的测试和 3.3.5-mac.1 都没有暴露（mac.1 的发布目录里也混着两个 OpenCV，但用的是 fp32 模型，不受影响）；v2 的 fp16 输入正好要用它。

修复：按导出的清单原样安装（`--no-deps`），并在构建时核对装上的包与锁文件完全一致，多一个、少一个、版本不同都会停下。现在的发布目录：63 个包，与锁文件一致，只有 headless 4.14。

| 场景 | 结果 |
|---|---|
| 新装（postinstall 的做法：放好模型，运行发布目录里的 `configure.sh`） | 准备模型 7 分 53 秒；没有下载任何模型；22 个进程没有打开 Homebrew 的文件；端到端 **42/42**（含 3 段 4K HDR / 1080p 视频、人脸、OCR、中文搜索、转码、备份） |
| 接管一键安装版 | 前后端到端都是 **42/42**；照片 34、人脸 1、搜索向量 29、OCR 38、用户 1、设置哈希全部一致；上一个版本保留 |

### 这台 Mac 的实际升级（`install.sh`，原来的模型，131 张照片）

| 项目 | 结果 |
|---|---|
| 预热 | 5 分 0 秒 |
| 删除旧导出 | 智能搜索 32 → 11 GB、人脸 1.8 GB → 707 MB、OCR 5.6 → 2.0 GB；模型目录 40 → 16 GB（剩下的是以前试过的其他模型） |

## 对正式环境的影响

- 第一次导入时：智能搜索和人脸转到 ANE，OCR 的检测也到了 ANE，GPU 只剩 OCR 的文字识别，所以 ANE 会有占用，GPU 不再满载，整体快一些
- 升级时需要重新下载 v2 模型约 4.3 GB（安装包里已经带了），第一次准备约 8–12 分钟（估算，M4 比 M4 Pro 慢），之后启动只需几秒
- 想换回原来的模型：`native.env` 里加 `IMMICH_NATIVE_MODEL_REVISION=main`，再运行 `immichctl warm`（会重新下载原来的导出）
