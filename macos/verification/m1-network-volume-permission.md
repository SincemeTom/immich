# M1-7 macOS 网络宗卷授权（访问群晖 NFS）

- 日期：2026-10-30
- 分支：`mac/fix/network-volume-permission`
- 结论：**通过**。服务端改为从固定路径 `<安装目录>/bin/node` 运行。网络宗卷授权只需要在 Mac 上点一次"允许"，以后升级不再询问

## 问题

macOS 有一项隐私授权叫"网络宗卷"（`kTCCServiceSystemPolicyNetworkVolumes`）：一个程序第一次读取网络盘（NFS、SMB）上的文件时，系统会弹窗问"node 想要访问网络宗卷上的文件"。在有人点"允许"之前，读取会**一直卡住**，不会报错。

原生部署的服务端由 launchd 在后台运行，读取群晖上的外部库时就会触发这个弹窗。Docker 部署没有这个问题，因为所有文件访问都在 Linux 虚拟机里进行。

## 实测（本机用 rclone 临时搭 NFS 服务模拟群晖）

测试方式和服务端完全一致：一个 LaunchAgent，脚本里 `exec node`，`PATH` 里放发布目录的 ffmpeg。node 依次执行：列目录、读文件算 SHA-1、写入并删除一个 `.xmp`、调用 `ffprobe`、通过 `exiftool-vendored`（`/usr/bin/perl`）读 EXIF。

| # | 情况 | 是否弹窗 | 结果 |
|---|---|---|---|
| 0 | 普通用户（不用管理员权限）用 `mount_nfs` 挂载 | — | 成功：后台服务也能自己挂载 |
| 1 | 当前发布目录的 node，已允许过 | 否 | 5 项全部成功；ffprobe 和 exiftool **继承 node 的授权**，不单独弹窗 |
| 2 | 同一个 node 复制到另一个路径 | **是** | 用户点允许之前，列目录一直卡住（约 27 秒） |
| 3 | 在第 2 项的路径上换成**另一个版本**的官方 node（v24.21.0，签名方同为 Node.js，Team `HX7739G8FX`） | 否 | 5 项全部成功，列目录 38 毫秒 |
| 4 | 新的固定路径 `<安装目录>/bin/node`，第一次使用 | 是（一次） | 用户点允许后成功；系统记录 `authValue=2`（允许） |
| 5 | 固定路径上换成 v24.21.0，模拟升级 | 否 | 5 项全部成功，列目录 39 毫秒 |

结论：

- 授权按**程序路径**记录，同时校验签名。签名方不变时，换版本不需要重新授权（第 3、5 项）。
- 原来每个发布目录都有自己的 node（`releases/<版本>/node/bin/node`），路径每次升级都会变，所以**每次升级都要重新点一次允许**，没点之前服务端读群晖会卡住（第 2 项）。
- ffmpeg 和 exiftool 由 node 启动，用的是 node 的授权（第 1 项）。ffmpeg 只有临时签名，如果要单独授权，每次升级都会失效；现在不受影响。
- 机器学习服务（Python）只接收服务端发来的图片数据，不直接读群晖；PostgreSQL 和 Valkey 也不碰群晖。

## 改动

`run-service` 启动服务端时，确保 `<安装目录>/bin/node` 和当前发布目录的 node 一致：不一致就复制一份，再用重命名替换（运行中的进程可能还在使用旧文件），然后从固定路径启动。用复制而不是软链接，因为 macOS 按链接解析后的真实路径记录授权。

- 升级、回退到旧版本时，都会自动换成该版本的 node，路径不变。
- 服务端的主进程和 API 子进程都从固定路径运行（用 `lsof` 确认过）。
- `immichctl uninstall --purge` 删除整个安装目录时，会一并删掉它。

## 你需要知道的

- 这台 Mac 已经对 `~/Library/Application Support/Immich/bin/node` 点过"允许"，以后升级不会再问。
- 换一台 Mac 安装时，第一次访问群晖时要在那台 Mac 的屏幕上点一次"允许"（或者通过远程桌面点）。
- 授权可以在"系统设置 → 隐私与安全性 → 文件与文件夹 → node → 网络宗卷"里查看和撤销。如果点了"不允许"，Immich 读群晖会直接失败，要到这里重新打开。
- 测试过程中也给几个旧路径（之前的发布目录、临时目录）授过权。这些记录在"文件与文件夹"里会显示成几个"node"，没有影响，可以不管。
