# M1-5 外部库与手机备份：重复照片

- 日期：2026-10-30
- 分支：`mac/feat/external-checksum`
- 结论：**通过**。在修复前的代码上 5/5 复现了问题（同一批照片在时间线上出现两次），升级后 24/24 通过：外部库的照片会被手机备份识别，不再重复上传；已经重复的照片会归入"重复项"页面，默认保留外部库的原件，一键清理后相册和收藏都保留下来。过程中还发现并修复了 Immich 原有的一个 bug：实况照片被交叉配错，导致外部库照片的动态视频在清空回收站时被删除

## 问题

把群晖的旧照片作为外部库挂到 Immich 上以后，手机开启备份，会把这些照片再上传一遍，时间线上每张照片显示两次。

原因有两层：

1. **外部库照片的"指纹"算的是路径，不是内容。** Immich 给每个文件算一个 SHA-1 校验值作为指纹。上传的文件按内容算，外部库的文件却按 `"path:" + 文件路径` 算（`library.service.ts` 的 `processEntity`）。手机 App 判断一张照片有没有备份过，是拿本地照片的内容指纹去比服务器同步下来的指纹，外部库的照片永远比不上，所以 App 认为这些照片还没备份。
2. **上传时的查重只查上传库。** 服务端的 `getUploadAssetIdByChecksum` 写死了 `libraryId IS NULL`，就算指纹对上了，也认不出外部库里的同一个文件。

官方在 v2.7.0 加了 `checksumAlgorithm` 字段（PR #26573），并在代码注释里把路径指纹标为 deprecated（准备淘汰），PR 说明写的正是"为了以后把外部库安全地迁移到内容指纹"，但还没有实际做迁移。这次改动按这个方向实现，以后和上游合并时冲突会比较少。

## 改动

| 位置 | 改动 |
|---|---|
| `LibraryService.handleAssetChecksum`（新任务 `LibraryAssetChecksum`，在库队列里运行，默认同时处理 5 个） | 读取文件，按内容算 SHA-1，把指纹算法记为 `sha1`；然后把内容相同的上传文件和它归入同一个重复项组 |
| 何时运行 | 新导入或被修改过的文件：随元数据提取一起运行。已有文件：每次扫描时，把还在用路径指纹的文件排进队列。所以升级后点一次"扫描"就会逐步全部算完，扫描中断也会接着算 |
| 外部库里两个文件内容完全相同 | 数据库要求同一个库里指纹唯一，所以第二个文件改用一个"内容相同"的标记，不会被每次扫描反复读取；第一个文件代表这份内容参与备份比对 |
| `AssetRepository.getUploadAssetIdByChecksum` | 查重时同时查外部库里按内容算过指纹的文件。没在回收站里的优先，上传的优先 |
| `AssetMediaService.uploadAsset` | 写入数据库之前先查一次。原来只靠数据库的唯一约束拦截重复，但这个约束管不到外部库 |
| `bulkUploadCheck`（网页、命令行用） | 同一个内容有多条记录时，回答不在回收站里的那条 |
| `suggestDuplicate`（重复项页面"建议保留"哪一个） | 文件大小相同时，优先保留外部库的那份 |
| `AssetRepository.findLivePhotoMatch` | 实况照片的照片部分优先配同一个库里的视频（见下文） |
| `LibraryService.relinkLivePhoto` | 修复旧代码交叉配错的实况照片：两边互换，各自换回本库的视频 |

## 发现的上游 bug：实况照片交叉配对

实况照片在 Immich 里是两个资产：一张照片，加一个隐藏的视频。两者靠 EXIF 里的 `livePhotoCID` 配对。负责配对的 `findLivePhotoMatch` 接收一个 `libraryId` 参数，却根本没用它，结果是按数据库返回顺序随便取一个。

同一张实况照片既在外部库、又被手机备份过一次时，系统里就有两张照片和两个视频。实测旧代码的配对结果：**上传的照片配了外部库的视频，外部库的照片配了上传的视频**。这样一来，按重复项建议删掉上传的那份并清空回收站，外部库照片的动态视频就跟着一起删了。另一边，上传的视频没有照片引用，一直留着。

修复分两部分：

1. 配对时优先同一个库里的视频（按库排序，不是硬性过滤，所以只有一边有视频的老数据仍能配上）。
2. 计算内容指纹时检查：外部库照片配的视频如果不在本库，而本库里有对应的视频，就和上传的那张照片互换视频，一次更新两条记录。

用 SQL 在真实数据库上核对过：插入一个上传的视频后，旧查询返回的就是这个上传的视频（会配错）；新查询对上传的照片返回上传的视频，对外部库的照片返回库里的视频。

**你的群晖库可能已经存在这种交叉配对。** 升级后第一次扫描时会自动纠正，日志里能看到 `Paired live photo … with the video … in its own library`。

## 对你迁移群晖的意义和步骤

1. 升级以后，在"管理 → 外部库"里对群晖库点一次"扫描"。所有文件会在后台通过 NFS 读一遍，算出内容指纹。千兆网络大约每 TB 需要 3 小时；新加的文件之后随扫描自动处理。进度可以在"任务"页的"库"队列里看。
2. 算完以后，"工具 → 重复项"会列出所有"外部库原件 + 上传副本"的组，建议保留的都是外部库那份。可以逐组看，也可以点"全部去重"。上传的副本进回收站，相册、收藏、评分、描述、标签会合并到外部库的照片上（这是官方原有的合并逻辑）。
3. 之后手机继续开着备份就行：群晖里已有的照片不会再传，新拍的照片照常上传到 Immich 的上传库。

## 注意和限制

- **只认得内容完全一样的文件。** 如果群晖相册当初备份时转换过格式（比如 HEIC 转 JPG），或者改写过文件，指纹就对不上。这类重复只能靠"重复项"页面原有的按画面相似度查找（需要机器学习），或者靠下一步做的"相似度极高自动堆叠"。
- **Immich 会往外部库目录里写 `.xmp` 文件。** 在 Immich 里改收藏、评分、标签、描述，或者合并重复项时，Immich 会在原照片旁边写一个 `原文件名.xmp`。这是官方原有行为，本次测试里写了 11 个。群晖 NFS 如果是读写挂载，群晖相册目录里就会多出这些文件；如果是只读挂载，写入会失败（记一条错误日志），这些信息只保存在 Immich 的数据库里。
- **同一个外部库里两个内容完全相同的文件**，只有一个参与备份比对，另一个照常显示。
- 第一次扫描会把整个群晖库读一遍，期间 NAS 和网络会比较忙。
- 测试用的是本机文件夹，不是真的 NFS（这台 Mac 没有管理员权限，开不了 NFS 服务）。按代码逻辑，NFS 下没有不同的路径：读文件用的是同一个 `hashFile`；"群晖断开"这一项模拟了挂载点消失的情况。真实 NFS 环境建议你在自己的群晖上先用一个小目录试一遍。
