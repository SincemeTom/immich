# M1-4 中文智能搜索模型与模型预热

- 日期：2026-10-30
- 分支：`mac/feat/ml-warm-clip`
- 结论：**通过**。`XLM-Roberta-Large-ViT-H-14__frozen_laion5b_s13b_b90k` 确实能用中文搜索，已设为原生安装的默认模型；安装时预热模型，修复了 M1-3 的"首次使用请求超时"

## 为什么换模型

Immich 默认的 `ViT-B-32__openai` 只懂英文。官方文档 `docs/docs/features/searching.md` 的 Chinese (Simplified) 表格里根本没有它；`XLM-Roberta-Large-ViT-H-14__frozen_laion5b_s13b_b90k` 在表中召回率 75.22%，标为 Pareto 最优。文档还说明 `xlm` 系列不管用户界面设置成什么语言都能理解查询文字，适合中英文混着搜。（`nllb-clip-large-siglip__v1` 中文召回率更高，79.7%，但它按用户设置的语言理解查询，不适合混搜。）

## 实测（`macos/scripts/m1_clip_eval.py`）

图库是 `e2e/test-assets` 里的全部 47 张图片，按服务端的做法先生成 1440 像素的 JPEG 预览图再送去编码（服务端送给机器学习服务的是预览图，不是原图）。30 条查询每条都有中英文两个版本，正确答案是看过每张图片后人工标的（拼图见 `/tmp/immich-m1/sheet/sheet.jpg`，没有提交）。"recall@k"指正确照片排进前 k 名的比例。

| | ViT-B-32__openai（CoreML） | XLM（CPU） | XLM（CoreML） |
|---|---|---|---|
| 中文 recall@1 | **6.7%**（2/30） | 90.0% | **90.0%**（27/30） |
| 中文 recall@3 | 16.7% | 96.7% | 96.7% |
| 中文 recall@5 | 20.0% | 100% | 100% |
| 英文 recall@1 | 90.0% | 90.0% | 90.0% |
| 英文 recall@3 | 96.7% | 100% | 100% |
| 图片编码（中位数） | 14.5 ms | 238.8 ms | **93.3 ms** |
| 文字编码（中位数） | 5.2 ms | 43.2 ms | **19.8 ms** |
| 进程内存 | — | 4.1 GB | 6.9 GB（同进程里还加载过 ViT-B-32） |

- 换模型后中文从基本不可用变成可用，英文不变差。
- XLM 没排第一的 3 条中文查询："嶙峋的石灰岩"第 2，"服务器机柜和网线"第 4，"微笑的女人"第 2。
- CoreML 和 CPU 的结果完全一致（47 张图片的向量余弦相似度最小 1.0000）。CoreML 快 2.2–2.6 倍，CoreML 能执行模型中 99% 以上的节点（例如 1229 个节点中的 1227 个），所以继续用 CoreML。
- 测试集只有 47 张图片，结论足以说明"能不能用中文搜"，但不能代表在大照片库里的精确召回率。

## 安装集成

| 入口 | 行为 |
|---|---|
| `install.sh`（新建数据库时） | 智能搜索模型设为 XLM，然后预热 |
| `install.sh --clip-model 名称` | 在已有照片库上切换到指定模型，然后预热 |
| `install.sh --no-warm` | 不预热，模型在第一次用到时再下载 |
| `immichctl clip-model` | 显示当前模型 |
| `immichctl clip-model 名称` | 切换模型并预热；照片库里已有照片时，提示去网页「管理 → 任务 → 智能搜索 → 全部」重建索引 |
| `immichctl warm` | 下载并准备当前设置用到的全部模型（智能搜索、人脸、OCR），显示进度 |

- **模型设置写在哪**：写进 Immich 自己保存设置的地方（`system_metadata` 表的 `system-config`），和在网页里保存效果完全一样。网页里仍然能看到、能修改。模型名会先对照服务端代码里的 `CLIP_MODEL_INFO` 校验。
- **向量维度**：XLM 是 1024 维，ViT-B-32 是 512 维。服务端重启时会按新模型调整搜索索引（实测变成 `vector(1024)`），旧模型的搜索数据随之清空，所以已有照片要重建索引。
- **为什么不能自动重建索引**：服务端的管理命令里没有排队任务的命令，只能在网页上点，或者调用需要管理员登录的接口。

### 预热怎么做

1. 先暂停机器学习服务和服务端（预热要用服务的端口；服务端在这期间发出的任务会失败）。
2. **下载**：按服务自己的规则（同一个目录、组织、版本，跳过 ArmNN/RKNN）用 `huggingface_hub` 下载，可以断点续传。下载完成后写一个标记文件，以后的预热不再访问网络。这一步失败也会继续往下执行，文件齐全时照样能用。
3. **准备**：用服务自带的预加载功能（`MACHINE_LEARNING_PRELOAD__*`）启动服务，它会把每个模型每种输入尺寸的 CoreML 版本都编译好，然后才响应 `/ping`。
4. 停止预热进程，恢复机器学习服务和服务端。

## 发现并修复的问题

| 问题 | 原因 | 修复 |
|---|---|---|
| 预热刚开始就退出，ml 和服务端停着，预热进程还在后台跑 | 进度行用 `grep` 取日志里最近一步；服务还没写出第一步时 `grep` 没匹配到，在 `pipefail` + `set -e` 下整个脚本退出 | 允许没有匹配；改用 EXIT 陷阱，任何原因退出都会停止预热并恢复服务 |
| 下载中途停不下来 | 下载时服务还在启动阶段，不响应 SIGTERM；而且下载器是脚本的子进程，只结束脚本会留下孤儿进程 | 预热放在独立进程组里（macOS 没有 `setsid`，用 `perl setpgrp`），停止时向整组发信号，10 秒后改用 SIGKILL |
| 下载被打断后，下次要从头再下 4.8 GB | 服务加载不了不完整的模型时，会删掉整个模型目录重新下载（`main.py` 里的 `Clearing cache`） | 预热先用 Hugging Face 续传下载，再交给服务准备 |
| 模型被重新下载后，文本编码器的 CoreML 产物丢了 | 删除目录时连同已经准备好的文本编码器产物一起删了，而预加载不会回头再准备已加载过的模型 | 日志里出现 `Clearing cache` 时自动再预热一遍 |

### 测试中自己踩到的坑

- 第一版恢复测试会把游隼照片**彻底删除**，这会连同文件一起删掉；恢复数据库只能恢复数据库里的记录，恢复不了文件。所以之后这张照片没有预览图，重建索引时报 `ENOENT`，搜不到它。这是 Immich 的正常行为，问题出在测试本身。已改为移到回收站。
- 在后台进程里测试 Ctrl-C 无效：从非交互 shell 启动的后台进程，SIGINT 一开始就被忽略，bash 也就没法捕获它。改用 SIGTERM 测试，它和 Ctrl-C 走同一个处理逻辑。

## 对后续的影响

- **打包（M3）**：可以把下载好的 4.8 GB 模型直接放进安装包，安装时就不用联网下载。但 **CoreML 编译产物和所在路径绑定**：把模型目录从测试实例移到正式安装后，预热时用了 1 分 58 秒重新编译（没有重新下载）。所以编译产物没必要打进包里，安装时在本机编译即可（M4 Pro 上约 2 分钟）。
- **跟进上游版本**：上游 `main` 的 `docker-compose.yml` 开始设置 `MACHINE_LEARNING_MODEL_REVISION: v2`，`v3.3.5` 还没有。以后跟进到带这项设置的版本时，`run-service` 要同步设置，下载步骤会按版本号算出新的目录。
- **第二台 Mac**（已有 1202 个资产）：
  ```bash
  cd ~/Documents/immich && git pull
  macos/native/install.sh --clip-model XLM-Roberta-Large-ViT-H-14__frozen_laion5b_s13b_b90k
  ```
  然后在网页「管理 → 任务 → 智能搜索」点「全部」。按图片编码 93 ms 估算，1202 张约 2 分钟再加读取预览图的时间。那台机器网速慢，4.8 GB 下载可能要几个小时；中途断了重跑 `immichctl warm` 会接着下载。
