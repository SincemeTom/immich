# M4 调研：Apple Vision 能给 Immich 加什么（M4-0 方案 A3）

- 日期：2026-11-01
- 机器：M4 Pro 64 GB，macOS 15.6，Xcode 26.2 SDK
- 状态：**调研**，没有改 Immich 的代码。工具：`macos/vision/probe.swift`（调用 Vision 的小程序）、`macos/scripts/m4_vision_eval.py`（评测）
- 结论：**值得做，但范围比方案里小。** 自动标签、美学评分、人物头像挑选、截图识别、二维码、宠物（猫狗）可以用；**文字识别和人脸都不要换**（都明显不如现在的模型）；Vision 的"工具类图片"判断误报太多，**不能直接拿来自动归档**。macOS 26 才有的文档识别、镜头脏污检测这台机器跑不了，要在测试机上验证（工具已备好，见文末）

| 数据 | 内容 |
|---|---|

## 1. 速度和内存

每张 1440 像素预览图，热启动中位数（24 张）：

| 请求 | Vision 自选硬件 | 只用 CPU | 用途 |
|---|---|---|---|
| 图像分类（1303 个标签） | 8.6 ms | 39.2 ms | 自动标签 |
| 美学评分 + 是否工具类 | 6.3 ms | 37.5 ms | 精选、封面、截图 |
| 动物（猫、狗） | 6.1 ms | 21.0 ms | 宠物 |
| 条码、二维码 | 10.6 ms | 31.4 ms | 工具类 |
| 人脸框 + 拍摄质量 | 6.1 ms | 21.1 ms | 人物头像 |
| 图像特征 | 6.4 ms | 37.1 ms | 宠物个体聚类（以后） |
| 文字识别 | 24.1 ms | 22.5 ms | （不建议用，见下） |
| **七项一起** | **60.8 ms** | 202.4 ms | |

- 除文字识别外，Vision 自选硬件比只用 CPU 快 3–6 倍，说明用上了神经网络引擎或 GPU
- 整个进程只占 **154 MB**（模型由系统提供，不进安装包）
- 建议用的四项（分类、美学、动物、条码）约 31 ms 一张：5 万张第一次处理约 30 分钟（M4 估计 40–45 分钟），之后只处理新照片

## 2. 文字识别：不换

| | 真实照片 | 合成 | 困难 | 困难·繁体 | 困难·日文 | 困难小字 12/15/18/22 px | 无字照片误读 | 每张 |
|---|---|---|---|---|---|---|---|---|
| **PP-OCRv6（现在）** | **58/58** | **58/60** | **52/60** | **8/12** | **10/14** | 80/79/94/93% | — | 60 ms |
| Apple，自动识别语言 | 38/58 | 56/60 | 26/60 | 3/12 | 7/14 | 20/36/56/60% | 2 行 | 87 ms |
| Apple，自动，最小字高 1/150 | 49/58 | 55/60 | 33/60 | 4/12 | 7/14 | 40/21/81/73% | 3 行 | 90 ms |
| Apple，指定简繁日英，1/150 | 47/58 | 48/60 | 29/60 | 4/12 | 4/14 | 33/14/75/67% | 4 行 | 84 ms |

- Vision 默认不读低于图片高度 1/32 的字（1440 像素图里约 45 像素），调到 1/150 后真实照片从 38 提高到 49，仍然差很多
- 典型错误：把相邻的两块路牌读成一行（"虹梅南路八都 金路"）、"Hongmei"读成"Hongmel"、"元江路"少了"路"
- PP-OCRv6 现在已经在神经网络引擎上运行，比 Apple 还快。**结论：保留 PP-OCRv6。** macOS 26 的文档识别（表格、段落结构）另测，见第 8 节

## 3. 自动标签：可以作为标签浏览，不能代替智能搜索

把 30 条查询换成用户会点的标签（事先选好，如"粉色的花"→`flower`、"雪山"→`mountain`），按标签置信度排序：

| | recall@1 | recall@3 | recall@5 |
|---|---|---|---|
| 标签（Vision 分类） | 50% | 70% | 70% |
| 智能搜索（CLIP，现在） | 90% | 97–100% | 100% |

- **有用的地方**：猫、喷泉、沙丘、雪、仙人掌、啤酒、店面、图表这类明确的东西都排第一；标签是固定的词表，适合做"按标签浏览"的列表（"动物""食物""花"）和网页上的筛选条件，智能搜索做不到这一点
- **不足**：
  - 9 条查询的照片根本没打上对应标签：猎隼被标成"岩石、蜥蜴、爬行动物"，城堡、服务器机柜、冰咖啡、彩色房子、玻璃花瓶、方山都没认出来
  - 词表里没有"鹅""山谷""黑白照片"这类概念
  - 很多标签太宽泛，没有意义：置信度 0.5 以上最常见的是 `structure`（59/125）、`outdoor`、`sky`、`wood_processed`、`utensil`
- 做法：只用置信度 ≥ 0.5 的标签，去掉一份宽泛标签黑名单，1303 个标签译成中文（要人工过一遍），写成 Immich 自带的标签"自动/动物/猫"，可以整组删除

## 4. 截图和文档：Vision 的"工具类"判断不能直接用来归档

| 方法 | 截图（32） | 拍下来的文档（10） | 图库误报（47） | 主库误报（78） |
|---|---|---|---|---|
| Vision `isUtility` | 20 | 5 | 7 | **16** |
| 分类标签（screenshot、document、receipt……）≥ 0.5 | 19 | 0 | 2（手写笔记、图表，本来就算） | 4 |
| 分类标签 `screenshot` ≥ 0.5 | 16 | 0 | 0 | 0 |
| **元数据：没有相机信息，且是 PNG 或正好是屏幕分辨率** | **32** | 0 | 1（PNG 图表，本来就算） | **0** |

- 主库被 `isUtility` 标记的 16 张里，大约 11 张是普通照片：砧板上的食物、带灭火器的室内、壁炉、货车、车窗。只有 5 张勉强算"记录类"（汽车仪表盘、包装盒、镜头盒、招牌）。按它自动归档，会把五分之一的真实照片藏起来
- 只看"没有相机信息"也不行：图库 47 张里有 19 张没有相机信息（网上下载的、导出时去掉了信息），所以要加上"PNG 或屏幕分辨率"
- 元数据规则的 32/32 有一半是这些截图本身的生成方式决定的（都是 PNG 或屏幕分辨率、都没有相机信息），真正要验证的是它在真实库里**不误报**：两个库里分别只有 1 张（本来就算工具类的图表）和 0 张。真实 iPhone 截图（PNG，EXIF 里有 `Screenshot` 标记）、安卓截图、经微信转发后被压缩改了尺寸的截图，要在测试机的报告里再看
- 二维码：6 张拍下来的小票、海报、车票上的二维码 **6/6** 全部读出

建议：

| 类型 | 判断 | 处理 |
|---|---|---|
| **截图** | 元数据规则（没有相机信息 +（PNG、iOS 截图标记或屏幕分辨率）），或者没有相机信息 + `screenshot` 标签 ≥ 0.5 | 打标签"自动/截图"；**可选**自动归档（设置里开关，默认只打标签） |
| 文档、小票、二维码 | `isUtility`、文档类标签、二维码，macOS 26 再加文档识别 | **只打标签**（"自动/文档""自动/二维码"），不自动归档 |

## 5. 美学评分：适合在相似照片里挑最好的

47 张图库照片和处理变差的副本比较（分数越高越好）：

| 变差的方式 | 副本得分更低 | 中位数降低 |
|---|---|---|
| 模糊 3 像素 | 41/47 | 0.30 |
| 模糊 8 像素 | 42/47 | 1.09 |
| 变暗 | 46/47 | 0.15 |
| 低对比 | 37/47 | 0.11 |
| 噪点 | 35/47 | 0.11 |

- 能可靠地分出"糊了""暗了"，可以用来给自动堆叠选封面、回忆里挑照片
- 分数的绝对值不能当"废片"标准：好照片之间分数差异本身就大（图库中位数 0.50），只在同一组相似照片里比较才有意义
- 主库的最低分和最高分照片在报告里，需要在真实的连拍上再确认

## 6. 人脸：不换 buffalo_l，只用它挑头像

| | 结果 |
|---|---|
| Vision 在整张合影里找人脸 | **0/45**（buffalo_l 45/45）：合影里的脸约 38 像素宽，Vision 把整张图缩小后再检测，小脸全丢；裁出一块就能找到 |
| 在 buffalo_l 找到的人脸周围裁图 | 34/45 |
| 人脸拍摄质量，随模糊变化 | 0.35 → 0.10 → 0.06（单人照）；0.67 → 0.47 → 0.14 → 0.07（另一张） |

Vision 不提供人脸身份向量，不能分人。用处只有一个：在 buffalo_l 已经找到的脸上算拍摄质量，挑最清楚的一张做人物头像。

## 9. 建议的做法

| 功能 | 做不做 | 依据 |
|---|---|---|
| 自动标签（中文，"自动/"前缀） | 做 | 明确的物体排得准；宽泛标签要过滤 |
| 截图识别 | 做：元数据规则为主；归档做成可选 | 截图 32/32、两个库误报 0 |
| 文档、二维码 | 做：只打标签 | 二维码 6/6；`isUtility` 误报多 |
| 美学评分 → 堆叠封面、回忆选图 | 做 | 模糊、变暗时 87–98% 能分出来 |
| 人物头像挑最清楚的脸 | 做（小） | 拍摄质量随模糊下降明显 |
| 宠物（猫狗）标签 | 做（小） | 猫 0.7 |
| 文档结构、镜头脏污 | 等测试机结果 | 需要 macOS 26 |
| 用 Apple 替换 OCR | **不做** | 真实照片 49/58 对 58/58 |
| 用 Apple 替换人脸 | **不做** | 合影 0/45，且不能分人 |

实现方式：

- **一个 Swift 小程序**（和 probe 一样，随安装包签名分发），由机器学习服务启动并常驻，通过标准输入输出传 JSON；服务端发预览图，和现在的智能搜索、人脸、OCR 一样经过机器学习服务。不用 PyObjC：macOS 26 的新请求只有 Swift 接口
- **服务端新增一个"内容分析"任务队列**（缩略图之后），结果存一张新表（标签、美学分、是否截图、二维码、版本号），写入标签和可选的归档；尽量不改上游已有的表，方便以后合并上游
- **网页设置**：每项单独开关；截图默认只打标签
- macOS 15 上自动跳过 macOS 26 的请求

工作量估计 2–3 周：Swift 程序和机器学习服务接入 2–3 天；服务端任务、表、迁移 3–4 天；标签翻译和过滤 1–2 天；截图规则和设置页 2 天；封面、头像 1–2 天；测试 2–3 天。

## 文件

- `macos/vision/probe.swift`：调用 Vision 的小程序，每行输入一个 JSON 任务，输出结果和耗时；`probe labels` 列出 1303 个标签
- `macos/scripts/m4_vision_eval.py`：`ocr`、`tags`、`utility`、`quality`、`faces`、`speed`、`all`，以及在任何 Mac 上生成报告的 `library`
- 本文的数字都可以用 `m4_vision_eval.py all --ppocr <m1_ocr_eval.py 的结果>` 重跑
