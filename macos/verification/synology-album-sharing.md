# 群晖照片相册同步：共享成员和别人加的照片

- 分支：`mac/feat/synology-albums`
- 日期：2026-11-04
- 结论：同步建的相册，按群晖上的共享关系共享给对应的 Immich 用户（查看 / 下载 / 上传 → 仅查看 / 可下载 / 可编辑）；别人加进相册的照片，在**他自己**的库里找到后代他加进来。认人只按两种方式：绑定了群晖账号，或用群晖 SSO 登录过 Immich，不按名字或邮箱对应；对应不上的人在报告里只写人数，等他加入后下一次同步补上。同步只改动、移出自己加的成员，所有者在 Immich 里手动加的成员不动。服务器单元测试新增 4 项（群晖相关共 132 项）、数据库测试新增 6 项（共 15 项）通过，网页测试共 13 项通过。用真实账号在正式服上同步还没做，见文末

## 怎么做的

| 部分 | 做法 |
|---|---|
| 读群晖 | 相册列表改用 `SYNO.Foto.Browse.Album list` v2，带 `additional=['sharing_info','thumbnail']`，共享成员和角色跟着相册一起读到。照片仍是 `SYNO.Foto.Browse.Item list` v1，每张带主人（`owner_user_id`）、文件夹、文件名、大小、时间 |
| 认人 | 共享成员（`sharing_info.permission` 里 `type` 是 `user` 的）和别人照片的主人，按群晖照片用户 ID 找 Immich 用户：① 他在 Immich 里绑定了同一个群晖（地址一样）的账号，绑定时记下的群晖照片用户 ID 一致；② 否则，他用群晖 SSO 登录过 Immich，`oauthId` 和群晖登录名一致（不分大小写）。都不是的就是“还不在 Immich 里”。账号自己不算成员 |
| 权限 | `view` → 仅查看；`download` → 仅查看，可下载；`upload` → 可编辑（只能加、移出自己的照片，不是管理者）。不认识的角色不共享 |
| 共享 | 对应上的成员，相册里没有的加进去，记进新表 `synology_album_user`（相册、用户、上次同步时群晖的角色）。群晖改了角色就跟着改；群晖不再共享给他，就移出相册 |
| 不动的成员 | 所有者在 Immich 里手动加的成员，同步不改权限也不移出；同步加的成员在 Immich 里被移出了，不再加回来（群晖的角色变了也不加）；群晖说相册是共享的、却没给共享信息时，成员都不动 |
| 别人的照片：找 | 照片还是他的，同步只是代他加进我的相册，和他在 Immich 里作为可编辑成员自己加的一样。只在**他自己**的库里找：他绑定了群晖账号时，用他自己的会话读这张照片的文件夹（我的会话读不到别人的文件夹），确认登录的确实是这个群晖用户，再在他的外部图库里按路径找，规则和自己的照片一样；没绑定、或按路径没找到时，在他的全部照片（含上传的）里按文件名（NFC、不分大小写）+ 大小 + 时间（群晖的 `time` 和 `localDateTime` 比，差 1 秒以内）找 |
| 别人的照片：对上多张 | 按名字、大小、时间对上多张时，依次用已在相册里的、在线的、外部图库的、路径最短的那张，报告里计数 |
| 别人的照片：范围 | 只用时间线和归档里的照片：锁定文件夹里的、回收站里的、实况照片的视频部分都不用。他自己的图库被删了的也不用 |
| 移出别人的照片 | 和自己的照片一样，同步加进去的、群晖相册里没了才移出。有成员的文件夹读不到（登录失败、钥匙串里没密码、绑定的账号换了人）时，他的照片这次不移出，只加不减 |
| 每次同步读几次 | 每个绑定了账号的成员，一次同步只登录一次，每个文件夹只读一次；他的照片索引也只建一次，多个相册共用 |
| 报告 | 别人加的照片：多少张、找到多少、几张在等主人加入 Immich、几张按名字对上多张；成员：加了、改了、移出了几位；还有几个群晖用户不在 Immich 里（只写人数，不写是谁） |
| 和手动操作一样的后续 | 成员变了也通知网页刷新（发给同步后的全部成员，不发邮件）；相册的“已更新”计数把成员变化算进去 |
| 数据库 | 新表 `synology_album_user` 并进这一组还没发布的迁移（`1793750400000-AddSynologyAlbums`）：相册删了、用户删了，记录跟着删 |
| 网页 | 账号设置 → 群晖照片 → 上次同步：多显示别人加的照片找到了几张、等主人加入的几张、对上多张的几张，成员的增减，以及还有几位成员不在 Immich 里、他们怎样能加进来 |

探测时的数据（只读）：别人加进我相册的照片 3049 张；共享成员一共 232 人次（查看 75、下载 88、上传 69）。

## 测试

| 测什么 | 结果 |
|---|---|
| 服务端单元测试：群晖角色对应 Immich 权限（三种角色、不认识的角色）；按名字、大小、时间找照片（大小写和 NFC、时间差 1 秒以内、对上多张时怎么选） | 新增 4 项，群晖相关共 132 项通过 |
| 数据库测试（真实 Postgres）：按群晖共享给对上的成员（绑定的和 SSO 登录的，对不上的只计数）；群晖改角色、不再共享时跟着变，手动加的成员保留，在 Immich 里移出的不再加回；别人的照片只从他自己的库里找（别人库里同名同样的照片不用），群晖移出后跟着移出；读不到文件夹时按名字 + 大小 + 时间找，同一张有两份时用路径短的、计数；成员登录失败时他的照片保留；锁定文件夹里的照片不用 | 新增 6 项，共 15 项通过 |
| 服务端全部单元测试 | 2841 项通过；`user.controller` 有 1 项偶尔报 `socket hang up`，单独跑两次都过，和这次无关 |
| 网页：上次同步结果里显示别人的照片、对上多张、成员增减、不在 Immich 里的人数 | 共 13 项通过 |
| 类型检查、lint、格式；迁移和表定义一致（`sql-tools migrations generate` 显示没有差异） | 通过。网页 eslint 的 `tscompat` 规则照旧关掉；svelte-check 的 7 个错误是原来就有的 |

数据库测试照旧用本机临时起的 Postgres（带 VectorChord），测试配置是临时的，没有提交。

## 还没做的

- 在正式服用真实账号同步一次。要看：
  - 报告里别人的照片找到了多少（探测时 3049 张，其中 3044 张的主人已用 SSO 登录过 Immich）；没找到的，是他的外部图库没挂对、按名字 + 大小 + 时间对不上（例如时区不同），还是文件不在他的库里；
  - 对上多张的有几张，选的那张对不对；
  - 共享成员加了几位、权限和群晖的一致；还不在 Immich 里的人数和探测时对得上；
  - 再同步一次，什么都不变（照片和成员的加入、移出都是 0）；
  - 在群晖上改一位成员的角色、取消共享给一位成员，再同步，Immich 跟着变；在 Immich 里手动加的成员不受影响。
- 只用 SSO 登录、没绑定群晖账号的成员，读不到他的文件夹，只能按名字 + 大小 + 时间找。如果正式服上这类对不上的多，再考虑让他绑定账号。
